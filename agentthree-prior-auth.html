Healthcare AI · Clinical intake → prior authorization

Three agents. One auditable prior authorization decision.

A Clinical Intake Agent, a Prior Authorization Agent, and a Clinical Decision Support Agent coordinate over Google A2A, reach clinical systems through MCP servers, and hand a grounded, cited recommendation to a human reviewer. No consequential decision is made without a clinician.

How to read this page. The Live run tab is a browser simulation: agent outputs, latencies, and tool responses are generated locally from fictional data. The SHA-256 audit chain is computed for real in your browser. The Build status tab states which backend components exist outside this simulation.
01 · The problem

Why prior authorization needs agents, not a chatbot

Fragmented evidence

The facts a reviewer needs sit across the EHR, medication lists, payer policy PDFs, and clinical guidelines. Staff assemble them by hand, and requests stall on missing documentation.

Policy matching is criteria work

Coverage policies are lists of conditions: diagnosis, duration of conservative therapy, exam findings, prior imaging. Each criterion must be checked against cited evidence, not summarized loosely.

Regulatory clock

CMS-0057-F sets prior authorization decision timeframes for impacted payers (72 hours urgent, 7 calendar days standard, from 2026) and requires FHIR-based Prior Authorization APIs from 2027. Speed has to come with traceability.

02 · Architecture

Agents talk over A2A; tools are reached through MCP

03 · Communication

Two protocols, two jobs

A2A · agent to agent

Each agent publishes an Agent Card describing its skills and endpoint. Agents hand work forward with JSON-RPC message/send, sharing one contextId for the case. Structured clinical context travels as a DataPart; the narrative rationale as a TextPart.

  • Task states: submitted → working → input-required → completed
  • input-required is how the system pauses for a human reviewer
  • Agents stay independently deployable and replaceable

MCP · agent to tools and data

Agents never query the EHR or policy store directly. They call narrow MCP tools such as fhir_search, rxnorm_normalize, and policy_search, each served by a FastAPI-based MCP server with its own identity and least-privilege scope.

  • Tool schemas constrain what a model can request
  • Servers return only the fields the task needs (PHI minimization)
  • Every call is logged with arguments hash and result hash

Design decisions

Choices a reviewer will ask about

Agents cannot deny

The Prior Authorization Agent can recommend approval or pend for information. Adverse determinations route to a licensed reviewer. This mirrors state and CMS expectations on clinician involvement in denials.

Criteria, not vibes

Policy criteria are retrieved as discrete, versioned chunks and evaluated one by one. Each verdict carries the evidence span and policy section it relied on, so a reviewer can disagree with a single line.

Why A2A between agents

Intake, authorization, and decision support have different owners, data scopes, and release cycles. A2A keeps them as separate services with explicit contracts instead of one prompt with three personas.

Why MCP for tools

One tool contract serves any agent framework. Each MCP server enforces its own authorization and field-level minimization, so the model only sees what the tool returns.

Evaluation

A labeled set of synthetic cases scores extraction F1, criterion-level agreement with clinician reviewers, citation validity, and end-to-end task success. Regressions block deploys in CI.

Failure handling

Tool calls retry with backoff and idempotency keys. If grounding fails or a source is unavailable, the case pends with the reason recorded rather than proceeding on partial evidence.
